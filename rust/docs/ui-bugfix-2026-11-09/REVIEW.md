# Независимый обзор protocol UI и Host control

Срез рабочего дерева в процессе параллельных изменений 2026-11-09; выводы относятся
к прочитанным версиям файлов, не к будущему итоговому head. Код не изменялся,
тесты и production процессы не запускались.

## Подтверждённые дефекты

1. **Старое состояние снова разрешает команды после reconnect.** В
   `rust/crates/icem-desktop/src/host.rs:58-63` ошибка Status/Console/Autostart
   выставляет `connected=false`, но не инвалидирует `protocols.fresh`. Следующий
   успешный Status в строках 94–96 возвращает `connected=true`, сохраняя старый
   protocol snapshot. `monitor.rs:350-364` и `monitor.rs:48-62` тогда снова
   разрешают операцию по старому снимку до завершения нового Get. Например,
   перезапущенный Host может иметь другое состояние или конфигурацию. Нужна
   проверка последовательности success protocol Get → disconnect → reconnect
   Status → новый protocol Get, включая отказ действия в промежутке.

2. **Визуальный OFF отправляет команду OFF.** `protocol_view.rs:107` вычисляет
   положение switch по `running`, а `monitor.rs:360-363` вычисляет действие по
   `enabled`. При `configured=true, enabled=true, running=false` переключатель
   выглядит выключенным, но нажатие посылает выключение. Такое состояние реально:
   `optional_consumers.rs:169-184` считает наличие владельца enabled, а
   `mqtt_consumer/mod.rs:25-32,55-67` начинает с disconnected и может переподключаться.
   Оператор не видит, что нажатие остановит включённого клиента. Управление должно
   однозначно отражать то же состояние, которое оно переключает, отдельно показывая
   реальный статус подключения/ошибку. Текущий тест `protocol_view.rs:145-155`
   закрепляет несовпадение, а не выявляет его.

## Что проверено и что не доказано

В прочитанном коде фоновый Get не устанавливает `mutation`, а ответ Get при
очереди Get → Set снимает только `get_pending` (`protocol_view.rs:42-68`);
`worker.rs` исполняет запросы последовательно. Действие после наблюдаемого
disconnect запрещено через `connected`, кроме описанного окна после reconnect.
Timeout/lost ACK не повторяет Set автоматически, закрытые до исполнения запросы
пропускаются (`protocol_control.rs:106-114`, `main.rs:591-597`). Неуспешная
остановка сохраняет owner в registry (`consumers.rs:47-53`). Это статическая
проверка, не доказательство всех межпоточных/runtime сценариев.

Визуальная приёмка Windows, реальные broker/OPC/sidecar fault и lost-ACK traces,
а также финальные тесты общего head не выполнялись в рамках этого обзора;
отсутствие такой приёмки само по себе не считается найденным дефектом.
