## Подтверждённое исходным кодом: Shell может выбрать не тот Web endpoint

**Class:** автоматическое определение dashboard endpoint для уже работающего Host (`apps/shell/src/main.rs`); явно заданный `--web-url` — соседний случай вне автоматического определения.
**Inv:** dashboard использует фактический endpoint текущего владельца Host, включая запуск с `--port`/`--ini` и смену владельца; проверка — изолированные Windows process-тесты.
**N+1:** один проверяемый источник фактического endpoint на границе Host→Shell; новые варианты запуска и reconnect проходят те же проверки, без дополнительных догадок по файлам.

`apps/host/src/main.rs:100–107,190–200` принимает штатные `--ini` и `--port` и использует их для web listener. Однако `apps/shell/src/main.rs:161–180,251–281` при отсутствии `--web-url` однократно читает `web_port` через `StationPaths::installed()`, не параметры уже работающего Host; `OnceLock` также не обновляется при смене Host. MSI shortcut без аргументов указывает на Shell (`installer/Product.wxs:83–84`, `WindowsInstaller.psm1:58`), а ensure признаёт уже готовый Host без повторного запуска (`crates/icem-web/src/host_client.rs:144–145`).

Воспроизведение на изолированном стенде: задать установленному INI web_port 8090, запустить Host `--port 8091` или `--ini` с другим web_port, затем открыть desktop shortcut. Shell подключается к Host pipe, но запрос dashboard направляет на 8090, а не 8091; при занятом 8090 возможно чтение чужого HTTP endpoint. Вариант через Host tray передаёт `--web-url` (`apps/host/src/windows.rs:61–65`), но лишь новому Shell: если Shell уже владеет singleton, новый процесс только сигналит `SHELL_SHOW` и завершает работу, не передавая свои аргументы (`crates/icem-desktop/src/monitor.rs:452–462`). Утверждение основано на коде, Windows-прогон не проводился.

Рекомендуемые regression cases: изолированный реальный Host с нестандартным портом и валидным отдельным INI, Shell без `--web-url`, проверка фактического dashboard; существующий Shell + tray Open Panel; смена Host с другим endpoint и проверка reconnect; отсутствие/исправление установленного INI. Сохранить существующие запреты автоматического повторного запуска и повторения mutations. Устройство передачи endpoint требует решения владельца кода; изменение frozen proto не предполагать автоматически.

## Release wiring и границы проверки

- `tools/Build-WindowsRelease.ps1:21,39–57` получает роли и имена бинарников из `installer/windows-payload.json`, собирает четыре пакета в Release с MSVC static CRT и формирует архив; конкретного дефекта builder по прочитанным исходникам не установлено. Изменение plan требует проверки согласованности runtime имён: `host_client.rs:34–40`, `host/src/windows.rs:61–65` используют фиксированные имена EXE.
- Payload (`installer/windows-payload.json:5–30,33–75`) плоско размещает Host, Shell, emulator и OPC DA sidecar; две иконки — в `assets`, разные каталоги Host/emulator — в `templates` и `emulator/templates`. Host без `--registry` ищет EXE-relative `templates/variable_registry.json` (`apps/host/src/main.rs:394–410`), а `Start-Host.ps1:5–9` передаёт тот же каталог явно. Следовательно, различие script/shortcut само по себе не доказывает дефект. Ошибка загрузки default registry, в отличие от явного `--registry`, допускает продолжение с пустыми именами и без sniffer; это наблюдаемая разница политики, не классифицированная здесь как регрессия без отдельного требования.
- Windows live source выбирается на основании `settings.mmf_path`/`mmf_name`, mutex default — `BUS_MUTEX` (`apps/host/src/main.rs:209–219,279–287`); для fixture выбирается другой source. Установленный Shell запускает соседний Host с `--autostart` (`host_client.rs:34–40`). Эти ссылки не доказывают работу настоящего AddIn или live MMF.
- OPC DA sidecar сознательно opt-in, путь в JSON разрешается относительно каталога файла конфигурации (`apps/host/src/opc_da_consumer/config.rs:20–45`), не автоматически относительно EXE. Конфигурация в другом каталоге с относительным `icem-opc-da-sidecar.exe` поэтому укажет на тот другой каталог. Это интеграционный риск/условие конфигурации, не доказанный дефект: installer/README.md:178–182 прямо описывает opt-in и незарегистрированные COM-компоненты.
- `tools/Test-WindowsRelease.ps1:43–55,76–90` проверяет relocated archive, но Host запускает fixture с явным `--registry`, Shell — заведомо неверным `--web-url`; штатные desktop shortcut → ensure → installed INI/live source/tray и живой dashboard этим smoke не покрываются. Отсутствие такого теста или реального SDK/hardware acceptance не является доказательством production-дефекта.

## Реализация discovery и незавершённая интеграция

`icem-web/src/server.rs` публикует фактический `local_addr` забинденного WebServer в общем `WebState`; `desktop_endpoint.rs` отдаёт только проверенный loopback endpoint на внутреннем HTTP/2 pipe, без маршрута в публичном TCP router. Unspecified bind преобразуется в соответствующий localhost; не-loopback конкретный bind не превращается в догадку. Нет слушателя/неподходящий адрес — явная ошибка, без fallback к INI. Shell без явного `--web-url` делает read-only discovery заново на каждый dashboard request, в том числе после reconnect. Явный `--web-url` остаётся приоритетным. Frozen proto и зависимости не менялись.

Владелец B изменил tray Open Panel: теперь Shell передаётся только `--pipe` (`apps/host/src/windows.rs:61–65`), без принудительного `--web-url`. Файлы B здесь не менялись. Нужны совместные process/UI проверки; соединение с HTTP listener после discovery не является атомарной проверкой идентичности процесса.

Добавлены тесты преобразования адресов, строгого decode, приватности маршрута, реального ephemeral bind, Windows pipe после смены владельца и приоритета явного override. Первый вызов Cargo обнаружил отсутствие cargo в PATH; следующий вызов с установленным toolchain остановлен после 30 секунд ожидания занятого build lock. `rustfmt` для изменённых Rust-файлов выполнен; это не compile/test evidence. Требуются минимум `cargo test --release --locked --offline -p icem-web desktop_endpoint` и тест Shell, затем Windows process/release acceptance на общем интегрированном head.

Дополнение по замечанию родительского ревью: публикация теперь создаётся worker-ом до ready и принадлежит RAII guard; при завершении снимается только собственная публикация по идентичности владельца, включая случай повторного использования порта. Добавлены тесты остановки listener при работающем pipe, последующего listener и недопустимости снятия публикации преемника старым guard.
