# Независимое время жизни Host: анализ Shell и запуска

## Результат

Причина первоначального сообщения «закрытие Shell завершает Host» не установлена. Обнаружен отдельный подтверждённый дефект: custom pipe Host использовал общий singleton/lifecycle и при завершении сигнализировал стандартный Shell. Исправлена идентичность Host IPC; фактическое закрытие окна Shell пока не проверено.

## Свидетельства

* `apps/shell/src/main.rs`: Shell использует `Launch::installed()` только для стандартного pipe; повторное соединение после единственной попытки не запускает новый процесс. `HostPort` владеет только runtime и gRPC streams, не управляет процессом и не посылает shutdown.
* `crates/icem-desktop/src/monitor.rs`: закрытие окна вызывает `cx.quit()` для Shell; Shell слушает собственное событие `SHELL_SHUTDOWN`, а не отправляет `HOST_SHUTDOWN`. Worker завершает свою очередь и ожидает уже выполняющуюся операцию; это не команда завершения Host.
* `crates/icem-web/src/host_client.rs`: запуск передаёт ровно `--autostart`, CREATE_NO_WINDOW и все три стандартных потока в null. `std::process::Child` используется лишь для проверки преждевременного выхода во время ensure; его Drop не завершает дочерний процесс. Обратная зависимость от унаследованных stdio отсутствует; влияние внешнего Windows job object этим не исключено.
* `apps/host/src/main.rs`: обычный `--autostart` без явного `--duration-ms` меняет исходное тестовое значение 10000 на 0 (без таймера). Явный duration и запуск только с `--station-config` могут ограничивать жизнь; это другие сценарии. Цикл Host также завершается по console stop, lifecycle close/restart, ошибке либо отключению очереди; причинная связь с закрытием Shell не доказана.
* `apps/host/src/windows.rs`: стандартный Host при завершении сигнализирует закрытие Shell; это направление Host → Shell, а не обратное. Custom Host теперь не сигнализирует этот Shell.

## Проверка и ограничения

Добавлен `installed_launch_is_persistent_autostart` в `crates/icem-web/src/host_client.rs`: проверяются имя exe и полный список аргументов, в том числе отсутствие `--duration-ms`; целевой Release тест PASS. Windows process test `apps/host/tests/independent_lifetime.rs` запускает отдельный launcher, который через `ensure_with` создаёт fixture-процесс и завершает работу после готовности, освобождая `Child`. После выхода launcher fixture отвечает на новую проверку и останавливается по файлу в уникальном тестовом каталоге; запасной срок жизни — 20 секунд. `cargo test --release --locked --offline -p icem-host-app --test independent_lifetime -- --nocapture`: PASS, 3/3. Этот тест не запускает настоящий Host и не обращается к production IPC. `cargo fmt --all` выполнен.

До исправления `Lifecycle::new` для любого `--rpc-pipe` сбрасывал общие `HOST_RESTART` и `HOST_SHUTDOWN`, singleton был общий, а `Lifecycle::drop` сигнализировал общий `SHELL_SHUTDOWN`. Теперь `HostIpcIdentity` сохраняет точные исторические имена стандартного pipe, для custom pipe формирует отдельные имена, не назначает ему стандартный Shell и применяется до загрузки INI. Перезапуск сохраняет те же argv. CLI стандартного Host не менялся. Для согласования case-insensitive Windows pipe и case-sensitive kernel events используется безопасная обёртка `RtlUpcaseUnicodeChar` из существующего windows-sys; преобразование однокодовыми UTF-16 единицами, не Rust/ICU и без расширений. Уникальные имена используют сам нормализованный pipe, не hash. Тест сравнивает с реальным Windows pipe ASCII, кириллицу, сигмы (σ и ς различны в проверенной системе), ß/SS и разные имена. Для имён длиной 240, 247, 248 и 256 символов тест проверяет создание всех трёх kernel objects для каждого имени, принятого Windows pipe API; хотя бы один длинный pipe обязан быть принят.

Windows Release: `console_stop`, `ensure_host`, `grpc_control` прошли по 1 тесту после перевода на имена соответствующего custom экземпляра; isolated PROGRAMDATA/LOCALAPPDATA. `early_identity_uses_option_pairs_and_last_pipe_without_config_io` PASS. Настоящий process test запускает два custom Host через два отдельных launcher с `ensure`, затем после выхода launcher проверяет RPC и независимую остановку по собственным событиям: PASS, 6/6 вместе с fixture, Unicode и длинными именами. Предыдущий прогон подтвердил функциональные проверки, но упал при удалении копии EXE с Windows error 32: pipe уже закрыт, а процесс ещё не выгружен. Добавлено bounded наблюдение освобождения копий перед очисткой, без повтора stop. Настоящее GUI-X, sentinel стандартного Shell (его создание в общей сессии небезопасно) и Windows job object остаются НЕ ПРОВЕРЕНЫ. Один прежний повтор упал с E0433 на незавершённой параллельной правке `icem-config`; последующая сборка успешна.

Нужны наблюдения конкретного запуска: argv Host и Shell, код выхода Host, журнал Host около завершения, его parent/job принадлежность и последовательность действий (X окна, X консоли, пункт tray). Агент A обнаружил sharing violation config.ini в отдельных живых запусках; причинность по отношению к закрытию окна не доказана. Этим исполнителем изменены Host/main и windows lifecycle, platform identity, native upcase и перечисленные тесты; CLI, tray и native MMF не изменялись.
